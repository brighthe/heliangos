# 微信归档与事实路由工作流

> 本文件是所有 AI 工具执行联系人建档、聊天归档和跨仓库事实路由时的唯一规则源。回复风格见 [wechat-writing-style.md](wechat-writing-style.md)；各运行时只保留触发方式和工具差异。

## 数据模型

微信模块按“联系人实体”保存沟通事件，业务仓库按“领域”保存由沟通确认的事实：

- `heliangos:wechat/contacts/`：人物关系、称呼、沟通口径、沟通层未决和聊天原文。
- `heliangos:career/dlut-postdoc.md`：博士后官方身份、行政生命周期和关键节点。
- `dut-institute-work`：研究院任务、计划、进度、会议结论和交付物索引。
- `dut-postdoc`：科研路线、文献认识、工作汇报和可复用技术知识。
- `soptx`：软件功能、缺陷、实现任务和验证结果。
- `workstation`：工具、环境、配置、安装和跨设备迁移。

聊天原文是沟通证据，不替代业务仓库中的当前状态；业务仓库保存足以独立执行的确认结论，并保留来源指针。

## 联系人元数据

每位联系人一个 Markdown 文件，统一存放在 `wechat/contacts/`，并使用：

```yaml
---
record_type: wechat-contact
person: <姓名>
contexts:
  - <场景>
related_repositories: []
---
```

`contexts` 表示相识或沟通场景；`related_repositories` 只表示稳定、持续的业务关联。单次事实路由不自动建立长期映射，不设置 `default_repository`。

## 联系人定位与建档

1. 按 frontmatter 的 `person` 搜索 `wechat/contacts/*.md`。
2. 只有一个结果时，读取该档案和近期聊天。
3. 出现同名结果时，根据单位、场景或消息上下文判断；仍无法唯一确定时询问用户。
4. 尚未建档时，先确认姓名和场景，再复制 `wechat/templates/contact.md`。
5. 默认文件名使用 `<姓名>.md`；同名时使用 `<姓名>--<机构>.md`。
6. 新建联系人或修改 `contexts`、`related_repositories` 后，同步更新两个 Markdown 索引。

## 归档聊天

1. 忠实转写截图或文字，不改写原话，不保存截图。
2. 以截图可见日期和时间为准；不确定时标“待确认”，不编造。
3. 与已有记录去重，只追加新增内容；非文字内容用 `[图片]`、`[文件]`、`[语音]` 等标记并简述。
4. 用户已经发送消息并提供截图或最终文本时，以实际发送版本入库，不用此前草稿覆盖。
5. 默认保留可见原文；只有用户明确要求时才脱敏。
6. 根据新增聊天更新人物档案、沟通口径和沟通层未决，不把业务计划全文复制到联系人档案。

新增聊天批次涉及外部领域时，可在日期小节下标注：

```markdown
> 关联：`dut-institute-work:hpc`
> 派生更新：`dut-institute-work:hpc/plan.md`
```

## 路由派生事实

归档后逐条判断是否形成已确认的新事实：

| 内容 | 去处 |
| --- | --- |
| 人物关系、称呼、回复偏好、聊天原文 | 当前联系人档案 |
| 博士后行政身份、系统节点、考核与出站要求 | `heliangos:career/dlut-postdoc.md` |
| 研究院任务、分工、计划、进度 | `dut-institute-work` |
| 科研路线、调研认识、工作汇报 | `dut-postdoc` |
| 软件功能、缺陷、实现与验证任务 | `soptx` |
| 工具、环境、配置与迁移 | `workstation` |

- 归属明确时，在同一任务更新对应事实源，并在联系人日期小节写入“关联 / 派生更新”。
- 一条聊天可以路由到多个仓库，但每个事实只在一个领域仓库维护正文。
- 归属不明、结论尚未确认或事实源冲突时，不写外部仓库，先说明候选去处并请求确认。
- 写兄弟仓库前读取其 `AGENTS.md` 和 README，遵守公开边界、事实源和工作树规则。
- 目标仓库缺失、无法读取或相关文件存在难以安全合并的未提交修改时，停止对应写入并报告。
- 自动路由不包含 commit、push，也不建立中央待办副本。

## 索引维护

- `wechat/indexes/by-context.md` 必须覆盖每位联系人的全部 `contexts`。
- `wechat/indexes/by-repository.md` 必须覆盖全部长期映射，并将空列表联系人列入“无长期仓库映射”。
- 索引只保存姓名与相对链接；人物档案和 frontmatter 是权威来源。
- 迁移、重命名或删除联系人时同步搜索并修复仓库内及兄弟仓库中的来源指针。

## 引用格式

跨仓库来源统一写为：

```text
repository:repo-relative-path#heading
```

例如：

```text
heliangos:wechat/contacts/李宁宁.md#2026-07-20
dut-institute-work:hpc/plan.md#协作与汇报
```

引用用于定位事实源，不复制正文，也不写死 `C:\workspace` 等机器路径。

## 内容与操作边界

- 不驱动微信，不替用户输入或发送消息。
- 聊天内容不因归档任务主动发送到其他外部服务；没有任务需要时不联网检索其中的人名或单位。
- 涉及金额、合作、承诺或对他人的评价时，转写仍保持原文；起草回复时从严措辞。拿不准的事实标“待确认”。

## 完成回报

完成后简要报告：

- 新增聊天条数和时间范围；
- 更新了哪些人物信息、沟通层未决或索引；
- 自动更新了哪些领域事实源；
- 哪些候选更新因归属不明、目标缺失或工作树冲突而未执行。
